# ADR-0002. Размещение базы данных TimeCapsule

**Статус:** принято для ЛР3.

## Контекст

TimeCapsule в ЛР2 хранил приложение, PostgreSQL и вложения на одном EC2. В ЛР3 веб-сервер должен принимать HTTP из интернета, а PostgreSQL должен обслуживать только приложение через сеть VPC. Для базы нужен предсказуемый адрес подключения при изменениях инфраструктуры.

## Варианты

| Вариант | Преимущества | Ограничения |
| --- | --- | --- |
| PostgreSQL на EC2 приложения | Меньше ресурсов, соединение по loopback | База и приложение делят CPU и диск, а обновление или отказ машины затрагивает оба компонента |
| Отдельный EC2 в публичной подсети | Раздельные процессы обслуживания и простой доступ к репозиториям пакетов | Требуется внимательно ограничивать входящие соединения. Публичный IPv4 создаёт ненужный для приложения путь из интернета и оплачивается |
| Отдельный EC2 в приватной подсети | Отдельный цикл обслуживания, приватный IPv4, доступ к PostgreSQL только от группы приложения | Для обновлений нужен выход через временный NAT. Отказ одной зоны по-прежнему затронет базу |

## Решение

Разместить PostgreSQL на `timecapsule-dev-db` в `private-a`, без публичного IPv4. Разрешить TCP 5432 от `timecapsule-dev-web-sg`, SSH от `timecapsule-dev-bastion-sg` и аутентификацию SCRAM для прикладной роли. Связать VPC с приватной зоной Route 53 и использовать `db.timecapsule.internal` в конфигурации приложения.

## Последствия

- Для обновлений добавляется временный зональный NAT Gateway. Учитываются часы работы шлюза, объём обработанных данных и его публичный IPv4. После обновления маршрут и шлюз удаляются, IPv4 освобождается.
- Elastic IP позволяет пользователю обращаться к приложению по постоянному адресу между остановками EC2. Если перед приложением появится публичный ALB, пользователи будут обращаться к DNS балансировщика, а Elastic IP приложения можно освободить.
- Вычисления EC2 можно остановить между занятиями. EBS, закреплённый IPv4 и приватная зона остаются отдельными ресурсами для тарификации.
- PostgreSQL и приложение находятся в одной зоне. Для отказоустойчивости потребуются цели приложения в разных зонах, общие хранилища для состояния приложения и конфигурация PostgreSQL, которая переживает потерю зоны.
